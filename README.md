# RAG + Evaluation: Comparing Retrieval Strategies

A small, fully working Retrieval-Augmented Generation system built to explore
and *measure* — not just demonstrate — how retrieval quality affects the
quality of LLM-generated answers.

Rather than another "chat with your PDF" demo, this project focuses on the
part of RAG that's usually invisible to end users: **how well does the
retriever actually find the right information, and how much does that
matter for the final answer?**

## What this project shows

- A from-scratch (no LangChain/LlamaIndex) RAG pipeline: document loading,
  chunking, dense (vector) and sparse (BM25) indexing, hybrid retrieval via
  Reciprocal Rank Fusion, and local LLM generation via Ollama.
- A hand-built **golden evaluation dataset** (15 questions with verified
  ground-truth source chunks) used to measure:
  - **Retrieval quality**: hit rate, recall, and MRR — independent of the LLM.
  - **Answer quality**: embedding-based answer correctness, and
    **groundedness** via LLM-as-judge.
- A head-to-head comparison of **vector search vs. BM25 vs. hybrid search**
  on the same corpus and the same questions.

## Architecture

```text
Wikipedia articles (20, English)
        │
        ▼
  loaders.py        → raw text + metadata
        │
        ▼
  chunker.py         → fixed-size chunks (200 words, 40-word overlap)
        │
        ▼
  embeddings.py       → sentence-transformers (all-MiniLM-L6-v2)
        │
        ▼
  indexer.py          → FAISS (dense) + BM25 (sparse) indexes
        │
        ▼
  retriever.py         → vector / bm25 / hybrid (RRF, k=60) search
        │
        ▼
  llm.py + rag_pipeline.py  → context-grounded answer generation (Ollama, llama3.2)
        │
        ▼
  evaluate.py           → retrieval metrics + answer quality metrics
```

## Dataset

**Corpus**: 15 English Wikipedia articles on algorithms and data structures
(quicksort, merge sort, BST, AVL tree, hash table, Dijkstra's algorithm,
dynamic programming, etc.) — a single, terminology-dense domain chosen
deliberately to make retrieval genuinely hard to get right (many articles
share vocabulary, so semantic vs. keyword matching actually diverge).

**Distractor set**: 5 unrelated articles (Italian cuisine, photosynthesis,
Renaissance, volcanoes, history of chess) added to the index without any
matching questions — used to sanity-check that retrieval doesn't surface
unrelated noise for in-domain queries.

**Golden dataset**: 15 manually written questions, each mapped to the
specific chunk ID(s) that should be retrieved to answer it. About a third
target the introductory section of an article; the rest deliberately target
mid-document, more specific technical content (e.g. AVL tree split/join
operations, quicksort's worst-case scenario) to avoid an artificially easy
retrieval task.

## Setup

**Requirements**: Python 3.10+, [Ollama](https://ollama.com) installed and
running locally with the `llama3.2` model pulled:

```bash
ollama pull llama3.2
```

Install Python dependencies:

```bash
pip install -r requirements.txt
```

## Usage

Build the corpus and indexes (downloads Wikipedia articles, chunks them,
builds FAISS + BM25 indexes):

```bash
python -m src.main build-index
```

Ask a single question:

```bash
python -m src.main ask "How does quicksort partition an array?"
python -m src.main ask "What is a complete graph?" --strategy bm25 --k 3
```

Run the full evaluation (retrieval metrics + answer quality metrics across
all three strategies):

```bash
python -m src.main evaluate
```

Results are printed to the console and saved to `data/evaluation/results.json`
(including per-question detail, not just aggregate scores).

## Evaluation methodology

**Retrieval metrics** (computed without invoking the LLM):
- **Hit rate@k** — was at least one expected chunk present in the top-k results?
- **Recall@k** — what fraction of expected chunks (for multi-chunk questions) were retrieved?
- **MRR** — how highly was the first correct chunk ranked, on average?

**Answer quality metrics** (require LLM generation):
- **Answer correctness** — cosine similarity between the generated answer's
  embedding and a hand-written reference answer.
- **Groundedness** — a second, independent LLM call (temperature=0, separate
  system prompt) judges whether the generated answer is fully supported by
  the retrieved context, returning a 0.0–1.0 score with a short justification.

## Results

Run on the 15-question golden dataset, k=5:

| Strategy | Hit Rate | Recall | MRR   | Answer Correctness | Groundedness |
|----------|----------|--------|-------|---------------------|--------------|
| vector   | 0.733    | 0.733  | 0.552 | 0.832               | 0.767        |
| bm25     | 0.600    | 0.600  | 0.472 | 0.838               | 0.733        |
| hybrid   | 0.667    | 0.667  | 0.422 | 0.849               | 0.900        |

### Key findings

- **Vector search retrieves the correct chunk most often** and ranks it
  highest on average (best MRR), which fits the corpus: several golden
  questions target conceptual/paraphrased content rather than exact
  terminology.
- **Hybrid search has a lower MRR than plain BM25**, despite a higher hit
  rate. This is a direct effect of how Reciprocal Rank Fusion works: RRF
  rewards chunks that rank reasonably well in *both* retrieval methods,
  which can push down a chunk that ranks extremely well in only one of
  them. Hybrid finds the right chunk more often, but doesn't always rank it
  as high as the single best method would.
- **Hybrid search produces the most grounded answers** (0.900) despite a
  weaker raw ranking — the context it retrieves, even if imperfectly
  ranked, appears to give the LLM a more consistent basis to answer from.

### Known limitations

- **The judge model is the same model used to generate answers**
  (`llama3.2` in both roles). This risks *self-preference bias* — a model
  may rate its own generation style more favorably than an external judge
  would. The code supports passing a different `judge_model`, which is a
  natural next step.
- Groundedness is judged against the **entire retrieved context**, not
  specifically against the chunks the model actually cited in its answer —
  a simpler, slightly coarser signal than citation-level verification.
- 15 questions is a small evaluation set; results should be read as
  indicative of behavior on this corpus, not as a statistically robust
  benchmark.

## Possible extensions

- Cross-encoder reranking on top of hybrid retrieval, with before/after recall@k comparison
- Comparing fixed-size chunking against heading-based (semantic) chunking
- Using a distinct model as judge to remove self-preference bias
- Citation-level groundedness (verifying only the chunks the model actually cited)
- Sweeping k and the RRF candidate pool size to see their effect on ranking quality
